# ClickHouse DDL v1

`plan` строит ALTER из метаданных PG и CH. `apply` заново строит план, проверяет все обнаруженные таблицы и выполняет его. Любой известный blocker или ошибка проверки до начала выполнения означает **ноль отправленных DDL во всём запуске**.

## Интерфейс

```sh
sync-pg2ch plan --config config.toml --format text
sync-pg2ch plan --config config.toml --format json
sync-pg2ch plan --config config.toml --format sql
sync-pg2ch apply --config config.toml --format json
```

Набор таблиц и сопоставление PG-источников совпадают с `diff`: обнаружение в CH-базе, исключения `[discovery]`, точное имя или PeerDB `schema_table` в выбранной PG-схеме. Неоднозначный или отсутствующий источник выбранной таблицы блокирует весь план. Исключённые таблицы перечислены в `skipped_tables`; если выбранных таблиц не осталось, команда завершается с exit 2.

Text и JSON показывают операции, SQL, движки базы и таблиц, причины блокировки. Заблокированный `plan --format sql` оставляет stdout пустым; причины идут в stderr. `apply` использует актуальные каталоги и не принимает сохранённый SQL или JSON-план на вход. Все форматы имеют версию `1`.

## Операции

| Состояние | Операция |
|---|---|
| Исходной PG-колонки нет в CH, тип поддержан | `ADD COLUMN name Nullable(T)` |
| Тип и nullable совместимы | Ничего |
| PG допускает NULL, CH не допускает | Добавить Nullable, сохранив существующий более широкий тип и LowCardinality |
| Не хватает диапазона signed integer | Расширить Int8/16/32 до подходящего Int16/32/64 |
| PG требует Float64, CH хранит Float32 | Расширить до Float64 |
| Не хватает precision/scale Decimal | Выбрать тип, вмещающий диапазон CH и требования PG |
| PG date, CH Date | Расширить до Date32 |
| Лишняя CH-колонка | Сохранить; `target_only_column` имеет статус `compatible` |

Для Decimal новая scale равна максимуму scale источника и назначения. Число целых цифр равно максимуму их ёмкости целой части. Если сумма превышает 76, план блокируется. Например, при PG `numeric(18,4)` и CH `Decimal(18,2)` нужен `Decimal(38,4)`: старое значение CH может занимать 16 целых цифр.

Новые колонки получают Nullable даже при PG NOT NULL. Старые строки читаются с NULL; backfill из PG не выполняется. Построение ALTER не читает пользовательские строки. Встроенная геометрия PG и PostGIS geometry/geography используют строковое представление по [матрице совместимости](compatibility.md).

Сужение, смена семейства типов, изменение timezone или точности timestamp не имеют автоматического ALTER-правила. DROP, RENAME, перестроение таблицы и перенос строк в набор операций не входят.

## Движки и зависимости

DDL поддержан на ClickHouse **25.8 и 26.8 LTS** для локальных `MergeTree` и `ReplacingMergeTree` в базах `Atomic`/`Ordinary`. Запрос отправляется через заданный endpoint без `ON CLUSTER`. Replicated/Shared-движки и Replicated database определяются по метаданным и блокируют необходимые изменения. Совместимая таблица без операций не требует поддержки DDL для своего движка; `diff` сохраняет собственную область поддержки.

| Метаданные | Условие блокировки |
|---|---|
| Sorting/primary/partition/sampling key | MODIFY затрагивает колонку ключа |
| Аргументы движка | MODIFY затрагивает version/is_deleted или аргументы не удалось разобрать |
| ALIAS/MATERIALIZED вместо колонки PG | Колонка не допускает обычную запись |
| DEFAULT/MATERIALIZED/ALIAS с вычислением | Выражение ссылается на изменяемую колонку или его зависимости не удалось определить |
| Codecs изменяемой колонки | MODIFY разрешён только с общими LZ4/LZ4HC/ZSTD/NONE или без явного codec |
| Индексы или projections | Любой MODIFY в таблице |
| TTL, constraints, зависимые materialized views | Любой ADD/MODIFY в таблице |
| Незавершённая mutation этой таблицы | Любой ADD/MODIFY |
| Активный ALTER на сервере | Любой ADD/MODIFY |

Литералы и простые выражения с известными скалярными функциями допускаются, если не зависят от изменяемой колонки. Например, `_peerdb_synced_at DEFAULT now64()` не мешает изменению `note`, а `DEFAULT id + 1` блокирует изменение `id`. Проверяются также служебные колонки, исключённые из diff. Неизвестные функции и синтаксис блокируют MODIFY с `unresolved_column_expression`; полный SQL-анализатор не реализован. Существующие DEFAULT, comments и codecs сохраняются сервером и повторно проверяются после команды.

## Проверка и выполнение

1. Прочитать весь набор CH-таблиц, PG-кандидатов и метаданные обеих сторон.
2. Построить типизированные операции и собрать blockers по всем таблицам. Проверить предполагаемую совместимость и сохранение диапазона CH-типов.
3. В `apply` проверить права на необходимые ADD/MODIFY. Повторно прочитать все снимки и список CH-таблиц. Изменение OID источника, UUID назначения, кандидатов, схемы или зависимостей блокирует запуск.
4. После успешной общей проверки выполнять таблицы последовательно, по одному составному ALTER на таблицу. Перед каждой командой повторно проверить её снимок.
5. Дождаться ответа с `alter_sync=1` и `wait_end_of_query=1`, проверить отсутствие незавершённых mutations, фактическую схему и сохранённые атрибуты. После всех ALTER выполнить итоговый diff.

Имена базы, таблицы и колонки экранируются отдельно. `IF EXISTS`/`IF NOT EXISTS` не скрывают конфликты. Повторный запуск читает актуальную схему; после успешного применения план содержит ноль операций.

PG остаётся read-only. Чтение CH использует `readonly=2`; проверка ALTER-прав и исполнитель используют `readonly=0`. Права перечислены в [README](../README.md#права).

`[apply].ddl_timeout_seconds` задаёт предел ожидания одной команды: по умолчанию 300 секунд, допустимо 1–86400. Он отделён от таймаута чтения каталогов. Приложение сохраняет `query_id` перед отправкой запроса.

## Исход выполнения

| Общий статус | Значение | Exit code |
|---|---|---|
| `ready` | План проверен, команды не отправлялись | 0 |
| `completed` | Изменения подтверждены или не требуются | 0 |
| `blocked` | До выполнения найдена проблема | 1 для известного запрета, 2 для неполной проверки |
| `failed` | Выполнение остановлено без подтверждённо завершённых таблиц | 2 |
| `partial` | Часть таблиц подтверждена, затем выполнение остановлено | 2 |
| `indeterminate` | Отправленный DDL не удалось подтвердить | 2 |

Состояния отдельных таблиц: `unchanged`, `not_sent`, `completed`, `failed`, `indeterminate`. Поле `after` содержит фактический diff, когда он прочитан. Ошибка после начала выполнения прекращает отправку следующих команд; подтверждённые результаты сохраняются в отчёте.

Timeout, разрыв соединения и ошибка проверки после ответа сервера дают `indeterminate`. Приложение не повторяет такой запрос автоматически. Перед повторным запуском проверьте `query_id`, `system.processes`, `system.mutations` и схему на сервере.

Проверка не блокирует чужой DDL между чтением и записью. Общей транзакции и rollback для нескольких таблиц нет; это соответствует [поведению ALTER и mutations ClickHouse](https://clickhouse.com/docs/reference/statements/alter). Приложение не останавливает CDC и не обновляет внутренние метаданные PeerDB.

## Тесты

GitHub Actions запускает Docker-матрицы PG 14 с PostGIS и без него, CH 26.8 LTS. DDL-тесты проверяют граничные старые значения, NULL в добавленных колонках, расширение Decimal, сохранение более широкого типа, LowCardinality, DEFAULT/comments/codecs, лишние колонки, идентификаторы, PostGIS и повторный apply.

Для блокировки всего запуска тесты создают разрешённую операцию в первой таблице и проблему в последней. Записывающий HTTP-прокси проверяет отсутствие отправленных ALTER. Отдельные сценарии меняют комментарий колонки между чтениями, отклоняют вторую команду и задерживают ответ после её выполнения на реальном сервере. Ошибка post-check проверяется отдельно от ошибки DDL.

Проверки запрещённой реплицируемой топологии и незавершённой работы выполняются unit-тестами метаданных; кластер с Keeper в тестах не поднимается. TLS-suite выполняет plan/apply с доверенным CA и проверяет отказ без доверия сертификату.
