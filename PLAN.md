# План sync-pg2ch

Статус: первая реализация CLI выполнена, 2026-11-05. Команды запуска и фактический интерфейс описаны в [README](README.md); правила ниже задают область v1.

CLI на Rust подключается к PostgreSQL и ClickHouse, находит таблицы в указанной CH-базе, определяет источники в выбранной PG-схеме и печатает diff схем. Проверка допускает расширения типов назначения по явной матрице совместимости. Допустимые отличия остаются в отчёте.

## Согласованные требования

- Rust; первый релиз работает с append-only таблицами.
- PostgreSQL 14; ClickHouse LTS.
- Интеграционные тесты с реальными серверами в Docker и матрицами совместимости.
- Основное окружение тестирования: GitHub Actions; базы запускаются через `services`.
- Направление проверки: PostgreSQL как источник, ClickHouse как назначение.
- Список таблиц берётся из ClickHouse; сопоставление по точному имени и правилу PeerDB `schema_table` в одной заданной PG-схеме (`public` по умолчанию).
- Более широкий тип ClickHouse допустим, если правило совместимости это подтверждает.
- Геотипы входят в первый релиз: PostGIS geometry/geography и встроенные геометрические типы PG, включая point/polygon.
- PeerDB не требуется для работы приложения; поддержано его стандартное правило имён назначения ClickHouse.

Далее зафиксированы требования v1. Под append-only понимается поток новых строк; приложение не проверяет историю INSERT/UPDATE/DELETE. Результат относится к схеме и выбранным правилам представления типов, а не гарантирует работу произвольного CDC-коннектора.

## Поведение v1

Вход: два подключения, ClickHouse database и PostgreSQL schema. Приложение получает список постоянных объектов из `system.tables` выбранной CH-базы и для каждого проверяет точное PG-имя и имя без префикса `<postgres.schema>_`. Оба кандидата ищутся только в заданной схеме. Имена не разделяются по точкам и не меняют регистр. Таблицы, существующие только в PG, не входят в область проверки. Системные CH-базы не допускаются; неподдержанные движки остаются в отчёте как unknown.

Для `public_orders` кандидатами служат `public.public_orders` и `public.orders`. При двух совпадениях возвращается `ambiguous_source_table`, unknown и exit 2 без выбора источника. При отсутствии кандидатов возвращается `source_table_missing` и exit 1. Правило `schema.table → schema_table` подтверждено [исходником PeerDB](https://github.com/PeerDB-io/peerdb/blob/8a3660f976c0845bff163ea123581e5cbdd8a5d7/ui/app/mirrors/create/handlers.ts#L383-L420). Произвольные переименования и overrides префикса назначения из mirror не восстанавливаются без явного mapping.

Выход: текст для человека или JSON для автоматизации. Для каждой выбранной пары сравниваются наличие таблиц, набор колонок, типы, nullable и возможность записи в соответствующую колонку CH.

Сравнение выполняется по именам колонок с сохранением регистра. Порядок колонок не влияет на результат; предполагается запись по именам. Переименование выводится как отсутствие исходной колонки и наличие дополнительной, без угадывания намерений.

Дополнительные колонки CH считаются структурным расхождением. Для служебных колонок предусмотрен общий явный список исключений колонок для всех найденных таблиц. Встроенных исключений по префиксу `_peerdb_` нет. Отчёт перечисляет заданные исключения. Исключение не может скрыть колонку, существующую в PG: такой конфликт конфигурации завершает проверку с ошибкой.

Утилита только читает метаданные. В v1 не входят применение или генерация DDL, сравнение строк, чтение WAL, управление CDC и постоянный фоновый процесс. Индексы PG, PK/FK, defaults и CHECK не сравниваются с ORDER BY, partitioning, TTL и codecs CH. Их семантика не эквивалентна.

Источник: обычные постоянные таблицы PG и колонки partitioned parent; обход дочерних партиций не нужен. Назначение: таблицы семейства MergeTree, включая ReplicatedMergeTree и ReplacingMergeTree. Engine не используется для вывода о фактическом наличии UPDATE/DELETE. Views, foreign tables и Distributed требуют отдельной поддержки; для них v1 возвращает `unknown`.

## Контракт результата

Правила типов и ожидаемые тестовые случаи находятся в [матрице совместимости](docs/compatibility.md).

| Результат | Значение | Влияет на успех |
|---|---|---|
| `match` | Совпадение после нормализации | Нет |
| `compatible` | Разрешённое отличие, например integer → Int64 | Нет, но отличие видно в diff |
| `mismatch` | Нарушено известное правило типа или структуры | Да |
| `unknown` | Тип, объект или преобразование не поддержаны | Да, проверка неполная |

Термин `mismatch` не означает, что CDC обязательно остановится. Например, лишняя колонка с DEFAULT нарушает согласованный набор колонок, хотя запись может продолжаться.

| Exit code | Условие |
|---|---|
| `0` | Все выбранные пары проверены; только `match` и `compatible` |
| `1` | Проверка полная, есть `mismatch` |
| `2` | Ошибка конфигурации/подключения/метаданных либо хотя бы один `unknown` |

При смешанном результате приоритет: `2`, затем `1`, затем `0`. Найденные отличия сохраняются и при неполном результате. Пустая CH-база даёт `no_tables_discovered`, отсутствующая база — `clickhouse_database_missing`; оба случая завершаются exit 2.

JSON содержит `report_version`, идентификатор политики, версии серверов и используемых расширений PG, полноту проверки, итоговый статус, счётчики и результаты по таблицам. Запись отличия содержит стабильный `code`, координаты колонки, исходное определение PG, ожидаемое представление CH, фактическое определение CH, статус и объяснение. У геоколонок сохраняются семейство типа, subtype, SRID и размерность, когда они заданы метаданными. Ошибки чтения не маскируются под отсутствующие таблицы.

Формат отчёта: `report_version = 1`. Поле таблицы `source` допускает `null` для неразрешённого источника, `source_candidates` содержит найденных кандидатов. Текст и JSON строятся из одного объекта отчёта. Сортировка стабильная: CH-база и таблица, имя колонки, код отличия. Диагностика идёт в stderr; stdout содержит только отчёт. Пароли и полные строки подключения в отчёт и диагностику не попадают. Технические ошибки после начала проверки также отражаются в JSON; при невалидных CLI-аргументах допустима только диагностика stderr.

## Интерфейс и конфигурация

Команда: `sync-pg2ch diff --config config.toml --format text|json`. Формат по умолчанию: `text`.

TOML содержит ссылки на переменные окружения для подключений, имя CH-базы, PG-схему, таймауты и исключения колонок. Значения секретов читаются из окружения. Пример формата:

```toml
config_version = 1

[postgres]
url_env = "PG_URL"
schema = "public"

[clickhouse]
url_env = "CH_URL"
database = "analytics"
user_env = "CH_USER"
password_env = "CH_PASSWORD"

[comparison]
policy = "pg-clickhouse-v1"
connect_timeout_seconds = 5
query_timeout_seconds = 15

ignore_target_columns = ["_peerdb_version", "_peerdb_is_deleted"]
```

Исключения в примере иллюстративны: необходимо перечислить фактические служебные колонки. Неизвестные поля конфигурации отклоняются. Таймауты положительные; отсутствие указанной переменной окружения является ошибкой. TLS с проверкой сертификата поддерживается обоими адаптерами; обычные подключения используются в изолированных Docker-тестах.

В v1 одна встроенная политика совместимости, без DSL преобразований и произвольных SQL-выражений. Индивидуальные mappings типов и переименования колонок можно добавить после проверки требований на реальных схемах.

## Структура Rust-приложения

Один crate с `lib.rs` и тонким `main.rs` позволяет тестировать правила без сети и запускать тот же код через CLI.

| Модуль | Ответственность |
|---|---|
| `config` | CLI/TOML, переменные окружения, валидация входа |
| `catalog::postgres` | Чтение метаданных PG 14 |
| `catalog::clickhouse` | Чтение метаданных CH LTS |
| `model` | Таблицы, колонки, исходные типы, нормализованные типы |
| `compatibility` | Сопоставление PG → CH и направленные правила расширения |
| `diff` | Чистое сравнение двух снимков по политике |
| `report` | Текст/JSON, стабильные коды и сортировка |
| `app` | Порядок операций, ошибки, полнота результата и exit code |

Предлагаемый стек: Tokio, Clap, Serde/TOML, SQLx с PostgreSQL, официальный crate `clickhouse`, `thiserror`. Интеграционные Rust-тесты подключаются к готовым сервисам через переменные окружения; запуск Docker не входит в их код. Конкретные версии библиотек и Rust toolchain закрепляются при создании каркаса вместе с `Cargo.lock`. ORM и compile-time SQL macros не нужны для запросов к системным каталогам.

Типы представлены enum/структурами, а не строками для сравнения. Исходная строка типа сохраняется для отчёта. Неизвестный тип сохраняется как отдельный вариант. Парсер CH разбирает поддерживаемые вложенные обёртки, параметры Decimal/DateTime64 и кавычки; неизвестные конструкции не превращает в String.

## Чтение метаданных

PG-адаптер читает `pg_catalog`: отношения, атрибуты, типы, typmod, nullable, identity/generated. Системные и удалённые атрибуты исключаются. У serial/identity сравнивается тип значения; sequence не копируется. Generated-колонки в v1 дают `unknown`, поскольку их доставка не входит в контракт приложения.

Типы PostGIS определяются по OID и принадлежности расширению через каталоги, а не по одному имени `geometry` или жёстко заданному OID. Адаптер сохраняет исходный `format_type`, typmod и доступные пространственные ограничения. Схема установки PostGIS может отличаться от public. Простые PG point/polygon отличает от geometry(Point,...)/geometry(Polygon,...). Для сопоставления с CH String пространственная библиотека в Rust не нужна: геометрические вычисления и декодирование строк не входят в приложение.

CH-адаптер читает `system.tables` и `system.columns`: имена, типы, engine и `default_kind`. Нормальная колонка с DEFAULT допускает сравнение типа. ALIAS/MATERIALIZED на месте исходной колонки даёт отдельный `mismatch`; другие неподдерживаемые виды колонок дают `unknown`.

Имена из конфигурации передаются как значения параметров запросов к каталогам. Динамический SQL с подстановкой пользовательских идентификаторов не нужен. Считываются найденные в CH пары; приложение не сканирует строки пользовательских таблиц.

Первичная проверка соединения и видимости метаданных выполняется отдельно от поиска таблиц. Если полноту видимости нельзя подтвердить, результат неполный, а не «таблица отсутствует». Минимальный набор grants закрепляется интеграционными тестами и README.

После чтения выполняется повторная проверка выбранных метаданных и набора PG-кандидатов. Изменение схемы даёт `schema_changed_during_check`, изменение кандидатов — `source_mapping_changed_during_check`. Список CH-таблиц также перечитывается; его изменение даёт `table_set_changed_during_check`. Эти случаи завершаются exit 2 с сохранением найденного diff. Это обнаружение части гонок, не атомарный снимок двух СУБД. Отчёт фиксирует состояние на момент чтения и не блокирует будущий DDL.

## Docker и матрицы тестирования

Начальная обязательная пара версий: **PostgreSQL 14 × ClickHouse 26.8 LTS**, с двумя конфигурациями PG: без расширений и с PostGIS. Поддержка других веток не заявляется без прогонов. Образы скачаны и проверены локально 2026-11-05. Фактические версии: PostgreSQL 14.24, PostGIS 3.6.4 и ClickHouse 26.8.36.3. Digest закреплены в workflow GitHub Actions.

| Сервер | Проверенный тег (digest в workflow) |
|---|---|
| PostgreSQL | `postgres:14.24-bookworm` |
| PostgreSQL 14 + PostGIS | `postgis/postgis:14-3.6`, с закреплением digest; ожидаемая версия PostGIS 3.6.4 |
| ClickHouse | `clickhouse:26.8.36.3-jammy` |

Для amd64 проверены образы, закреплены digest и фактические версии серверов. Образы задаются в `strategy.matrix.include` workflow GitHub Actions и подставляются в `services`. Это единственный источник версий тестового окружения. Теги `latest`, `lts` и голый `14` не используются в обязательных тестах. Обновление patch-версии требует полного прогона той же матрицы.

GitHub Actions запускает PostgreSQL и ClickHouse как service containers на Ubuntu runner и удаляет их после job. Health checks проверяют готовность серверов до тестов. Rust-тесты запускаются на runner, получают endpoints через env и используют опубликованные порты сервисов. Каждая matrix job получает отдельную пару серверов; сценариям внутри job выделяются отдельные schema/database или уникальные имена.

Матрица содержит записи `pg14` и `pg14-postgis`, обе с одним закреплённым CH LTS. Базовые и встроенные geo-кейсы выполняются в обеих; PostGIS-кейсы обязательны в `pg14-postgis`. Setup создаёт расширение в fixture database и проверяет его версию, не полагаясь на наличие расширения в template database. Отсутствие ожидаемого PostGIS завершает job ошибкой. В plain PG job проверяется работа приложения без PostGIS. Для образа PostGIS используется поддержанный amd64 runner.

Testcontainers и отдельный Compose-harness не используются. При ручном воспроизведении те же тесты можно направить на самостоятельно запущенные базы через env. Для TLS-кейсов шаг CI генерирует тестовый CA и сертификаты, устанавливает конфигурацию сервисов и проверяет их готовность после перезапуска; Rust-тесты проверяют клиентские подключения.

Fixture описывает PG DDL, CH DDL, ожидаемые findings и exit code независимо от production mapper. Проверка собственного сгенерированного DDL не заменяет независимые ожидания. Администратор создаёт fixtures; приложение запускается с ограниченными правами.

| Группа | Обязательные случаи |
|---|---|
| Типы | Каждая поддержанная пара, widening/narrowing, signed/unsigned, Decimal precision/scale, временная точность/timezone |
| Nullable | Все четыре сочетания; DEFAULT не скрывает запрет NULL |
| Структура | Missing table/column, extra column, rename, другой порядок, несколько пар |
| Идентификаторы | Регистр, пробелы, точки, кавычки, Unicode, одинаковые имена в разных PG schemas |
| Каталоги | Удалённый PG-атрибут, identity, generated, DEFAULT/MATERIALIZED/ALIAS CH, partitioned parent |
| Геотипы | Все встроенные PG geo-типы; PostGIS geometry/geography, Point/Polygon/MultiPolygon и другие подтипы, typmod/SRID/Z/M, nullable; PostGIS вне public; одноимённый пользовательский тип |
| Неизвестное | Массивы, domains, enum, unconstrained numeric, неизвестный CH-тип и неподдержанный объект |
| Ошибки | Credentials, недостаточные grants, timeout, недоступный сервер, наблюдаемое изменение DDL |
| TLS | Оба адаптера: подключение с доверенным CA; отказ при недоверенном сертификате и несовпадении имени хоста |
| CLI | Text/JSON, сортировка, коды возврата, автообнаружение без списка таблиц, пустая/отсутствующая база, изменения списка, точные имена и заданная PG-схема, отсутствие секретов |
| Только метаданные | Для PG и CH: доступ к нужным метаданным при запрете SELECT пользовательских строк и DDL/DML; успешный запуск CLI и контроль неизменности схем |

Для разрешённых расширений чисел отдельные небольшие fixtures проверяют граничные конечные значения и сохранение точности при записи/чтении CH. Для дат и времени проверяются границы выбранного правила на закреплённом LTS. Эти операции выполняет тестовый harness; приложение данные не читает и не переносит. Тесты не доказывают корректность сериализации произвольного CDC.

Быстрые unit-тесты покрывают нормализацию, правила и свёртку статусов. GitHub Actions содержит job для fmt/Clippy/unit и обязательную integration job с матрицей сервисов. Отсутствие endpoints или неготовность базы является ошибкой, не причиной молча пропустить тесты. При падении шаги CI сохраняют версии образов, логи service containers и фактический JSON как artifacts.

## Этапы реализации

Каждый этап начинается с проверяемых случаев и заканчивается указанным результатом.

| Этап | Работа | Критерий завершения |
|---|---|---|
| 1. Каркас | Crate, CLI/config, модели отчёта, toolchain, workflow GitHub Actions с matrix/services | Оба сервера готовы в CI; тесты получают подключения через env; закреплены версии и digest |
| 2. Каталоги | Два адаптера, идентификаторы, права, TLS, нормализация типов и метаданные PostGIS | Независимые Docker-fixtures дают ожидаемые метаданные с расширением и без него; нет чтения пользовательских строк обеих СУБД; TLS-кейсы проходят |
| 3. Сравнение | Матрица типов, nullable, структура, исключения, unknown | Unit/Docker-матрицы подтверждают match/compatible/mismatch/unknown |
| 4. CLI end-to-end | Отчёт text/JSON, итоговый статус, частичные ошибки, повторная проверка метаданных | Запуск бинарника даёт ожидаемые findings и exit code на каждой группе fixtures |
| 5. Выпуск | CI, пример config, README, ограничения и поддержанные версии | Форматирование, Clippy, unit и Docker suite проходят; сценарий запуска воспроизводим |

Обязательные проверки реализации: `cargo fmt --all -- --check`, `cargo clippy --all-targets --all-features -- -D warnings`, unit-тесты и отдельный Docker integration target. Команды тестовых targets зафиксированы в README и workflow. Локально прошли 24 unit-теста, обе Docker-матрицы (158/174 случая), отдельные TLS-проверки обеих конфигураций и actionlint. Сценарии гонки DDL и таймаута используют детерминированный HTTP-каталог; это не воспроизведение всех возможных гонок на живом сервере.

## Что учтено из исследования

Ближайший универсальный аналог, [FoxSchema](https://github.com/tedious-code/foxschema), заявляет cross-dialect diff и поддержку PG/CH. [Atlas](https://atlasgo.io/guides/clickhouse) и [chschema](https://github.com/PostHog/chschema) дают ориентиры для управления и сравнения схем CH. Их практическая работа на наших сценариях не проверена.

В [ClickPipes](https://clickhouse.com/docs/integrations/clickpipes/postgres/schema-changes) часть schema evolution встроена в CDC. [Kafka Sink](https://clickhouse.com/docs/integrations/kafka/clickhouse-kafka-connect-sink) требует подготовленную таблицу назначения. Поэтому собственная утилита сосредоточена на независимой проверке существующей пары баз, с объяснимыми правилами и тестами. Утверждение об отсутствии альтернатив в план не закладывается.

Источники выбора окружения: [релиз ClickHouse 26.8 LTS](https://presentations.clickhouse.com/2026-release-26.8/), [официальные теги ClickHouse](https://github.com/docker-library/docs/blob/master/clickhouse/README.md), [официальные теги PostgreSQL](https://github.com/docker-library/docs/blob/master/postgres/README.md), [PostgreSQL services в GitHub Actions](https://docs.github.com/en/actions/tutorials/use-containerized-services/create-postgresql-service-containers), [контексты matrix/services](https://docs.github.com/en/actions/reference/workflows-and-actions/contexts). Основания выбора библиотек: [ClickHouse Rust client](https://docs.rs/clickhouse/latest/clickhouse/), [SQLx](https://docs.rs/sqlx/latest/sqlx/).

Образ для spatial-кейсов: [PostGIS Docker](https://github.com/postgis/docker-postgis). Выводы исследования геотипов и ссылки на подтверждающие тесты PeerDB находятся в [матрице совместимости](docs/compatibility.md#геотипы).
